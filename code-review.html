Code Review

Before changing any code, I reviewed Travlr Getaways exactly as I had submitted it for CS 465. The recording walks through what the application did, analyzes the code against the course’s code review checklist, and sets out the planned enhancement for each of the three categories: software design and engineering, algorithms and data structures, and databases.

Recorded for Milestone One, before any enhancement. The application has since been renamed Azamat School Admin.

What the review covers

The review takes each category in the same order: the existing functionality, an analysis against every section of the checklist (structure, documentation, variables, arithmetic operations, loops and branches, and defensive programming), and the planned enhancement with the course outcomes it supports. Where a checklist section does not apply, the review says so rather than skipping it.

  • Software design and engineering: the application’s three parts, the trip controller, the token middleware, the travel page controller and the user model.
  • Algorithms and data structures: how the trip controller reads data, and the absence of any logic that compares one record with another.
  • Databases: the two Mongoose schemas and their indexes, the seed script, and the template that renders database content on the public travel page.

Opening

Hello. My name is Azamat Soliev, and this is my code review for CS 499, Milestone One.

The artifact I'm reviewing is Travlr Getaways. It's a full-stack web application I built as the final project in CS 465, Full Stack Development, last term, in July and August of 2026.

I'm using this one artifact across all three categories, which the guidelines allow.

Category One is Software Design and Engineering. Category Two is Algorithms and Data Structures. Category Three is Databases.

For each one, I'll do three things. First I'll describe what the code currently does. Then I'll analyze it against the course code review checklist. Then I'll explain what I plan to enhance, what skills that demonstrates, and which course outcomes it aligns with.

The enhancement plan I'll be referring to is the one I submitted and had approved in Module One.

Let's start with Category One, Software Design and Engineering.

Software design and engineering: existing functionality

Travlr Getaways is a MEAN stack application. MEAN stands for MongoDB, Express, Angular, and Node.js, which means the whole thing is written in JavaScript, from the database all the way up to the browser.

Looking at the folder structure, there are three main parts, and they're deliberately separated.

app_server is the public-facing customer site. It's server-rendered using Handlebars templates, which means the server builds the finished HTML page and sends it to the browser.

app_api is the REST API. Both front ends talk to it.

And app_admin is the Angular administrative application. That one is a single-page application, so it updates parts of the page without reloading.

app.js is what wires everything together. It registers the static files, sets up the view engine, and mounts the route files.

This is the routes file for the API. Here's the part that matters.

The GET routes are open. Anyone can read the trips. But POST, PUT, and DELETE all have authenticateJWT in front of them. That's a middleware function, which means it runs before the actual request handler and can stop the request. In this case it checks for a valid login token.

So authentication is JWT-based. JWT stands for JSON Web Token. When an administrator logs in, the server gives them a signed token, and their browser sends it back on every request that changes data. Passwords are hashed and salted before storage, never kept in plain text.

So that's what the application does today. A public browsing site, a secured administrative interface, a shared API between them, and all of it operating on a single entity, which is a trip.

Software design and engineering: code analysis

Now I'll analyze this code against the course code review checklist. I'll go through the sections in order, and where a section doesn't apply to this project, I'll say so rather than skipping it.

Starting with Structure.

This is the trips controller. There are five functions in here: tripsList, tripsFindByCode, tripsAddTrip, tripsUpdateTrip, and tripsDeleteTrip.

And if you watch them go past, every single one has the same shape. Authorize the request. Run a query. Check whether the result is empty. Return a status code.

The checklist asks whether there are blocks of repeated code that could be condensed into a single procedure. There are, and this is the clearest example in the whole project. Five functions repeating one pattern.

Here's a genuine defect. This is in the JWT middleware.

On this line, the code takes the authorization header and splits it on a space.

Then on line 17, it checks whether the result has fewer than one element.

That check can never be true. Splitting a string always returns at least one element, even if the string is empty. So this entire branch is unreachable code. It can never run.

And the checklist asks directly about unreachable code.

There's a second problem on line 19. When it does return, it returns HTTP 501. That status code means "Not Implemented." The correct code for a missing or malformed token is 401 Unauthorized, which is actually what the surrounding checks return.

So this branch is both unreachable and returning the wrong status code.

One more structural finding. Line 4.

The API address is written directly into the code as a string, pointing at localhost on port 3000.

The checklist asks whether symbolics are used rather than magic number constants or string constants. Here they aren't. This value should come from configuration. As written, deploying this anywhere would mean editing the source code by hand.

That's Structure. Moving on to Documentation.

The comments that exist are accurate and consistent with the code, which is what the checklist asks. But there are no file headers showing intent, decision, or authorship, and the commenting gets thinner in the later files. That's something I'll clean up for the final portfolio.

Next, Variables.

I want to be honest about what this code does well, not just what's wrong with it. The variable and function naming is consistent and meaningful throughout. tripsList, tripsFindByCode, authenticateJWT — you can tell what each one does from its name. There are no redundant or unused variables that I found. This section is fine.

Next, Arithmetic Operations.

This section does not apply to this artifact. There's no floating-point comparison anywhere, no division, no rounding, and no arithmetic on numbers of very different magnitudes. I'm stating that explicitly rather than passing over it.

Next, Loops and Branches.

The branching is generally complete and correctly nested. The unreachable branch I showed you a moment ago is the one exception.

And finally, Defensive Programming.

Some of this section doesn't apply either. The questions about pointers and about memory allocation and deallocation are not relevant here, because JavaScript is garbage collected. There's no manual memory management to get wrong.

But the question that does apply is whether imported data and input arguments are tested for validity and completeness. Beyond what the Mongoose schema enforces, request bodies aren't validated.

There's a security finding here too. Line 22.

Passwords are hashed using PBKDF2 with SHA-512, which is a reasonable choice. But look at the iteration count. One thousand.

The iteration count is what makes password hashing slow on purpose, so that an attacker who steals the database can't test guesses quickly. One thousand iterations is far below current guidance for this algorithm. So the approach is right, but the work factor is much too low.

And here's the most important finding in this category.

This is the entire user schema. Email. Name. Hash. Salt. That's it.

There is no role field. Nowhere in this application does a user have a type.

So the application has exactly one kind of authenticated user, and a single binary permission state. You're either logged in, or you're not. There's no way to say that this person can do one thing and that person can do another.

That is the central design limitation of this artifact, and it's what my enhancement addresses.

So to summarize my findings for Category One. Repeated controller logic across five functions. An unreachable branch returning the wrong status code. A hardcoded configuration value. A password work factor well below current guidance. And no concept of user roles at all.

Software design and engineering: planned enhancement

Now, my planned enhancement for this category, which was approved in my Module One plan.

First, the reason behind it, because it isn't just an exercise. A teacher I know recently opened a small language school, and she runs everything manually right now. Student records, scheduling, attendance, tuition. This enhancement repurposes Travlr into software she could actually use to run that school.

So the plan does this.

It adds five new entities: Student, Teacher, ClassSession, Payment, and Attendance.

Instead of writing that repeated controller shape five more times, I'm building one generic controller factory. It takes a data model plus a configuration describing which role each action needs, and it produces all four handlers for that model. Same idea on the Angular side: one configuration-driven component instead of five nearly identical ones. That pattern is what makes five entities achievable inside a single module.

Then it adds three roles: owner, accountant, and teacher. Owner inherits everything the other two can do. The role is stored on the user record and included in the signed token. New registrations default to teacher, and only an existing owner can promote somebody.

And here's the part I want to highlight, because I found it while writing the plan rather than after building it.

Checking the role is not enough. If a teacher passes a role check, they'd then receive every teacher's class sessions and every student record, because the role condition is satisfied even though the records don't belong to them. That's called horizontal privilege escalation.

So the configuration also carries a record-level scope rule. For a teacher, every list query is constrained to records they own, and ownership is verified on the specific record before any update or delete.

Related to that: when a record exists but isn't yours, the response is 403 Forbidden, not 404 Not Found. That's deliberate. A 404 would confirm to an unauthorized caller that the record exists.

Deletion also becomes a soft delete. Removing a student marks the record inactive instead of erasing it, so their attendance and payment history isn't orphaned.

And the two defects I found earlier get fixed here: the iteration count goes up, and the hardcoded URL moves into configuration.

The specific skills this demonstrates are designing a scalable architecture instead of duplicating logic, building a permission model that combines role-level and record-level checks, identifying a security gap during design rather than after implementation, and choosing status codes that don't leak information.

This aligns with Course Outcome One, building collaborative environments that support organizational decision-making, because the owner, the accountant, and the teacher each get a purpose-built view for their own decisions instead of one undifferentiated interface.

It aligns with Course Outcome Four, using well-founded and innovative techniques to deliver value, because the generalized configuration-driven pattern is what makes a five-entity platform deliverable in the time available.

And it aligns with Course Outcome Five, developing a security mindset that anticipates adversarial exploits, because the access boundaries are enforced by design — through role inheritance, record-level ownership scoping, a restricted registration path, and status codes chosen so they don't reveal what exists.

That completes Category One. Next is Category Two, Algorithms and Data Structures.

Algorithms and data structures: existing functionality

This is Category Two, Algorithms and Data Structures.

The starting file is app_api/controllers/trips.js. That's the same controller file I looked at in Category One, but this time I'm looking at what it does with data, rather than how it's organized.

Line 11. This is tripsList.

It calls find with empty braces. Empty braces mean no filter at all. So this returns every single document in the collection, on every request.

And the comment on that line says exactly that. "No filter, return all records." It's an honest comment. It's also the finding.

Line 37. This is tripsFindByCode. It matches one trip by its code. That field is indexed, so this one is efficient, but it's still just a single-key lookup.

And that's the complete data-access story in this application. Return everything, or return one record by exact key.

Algorithms and data structures: code analysis

Analyzing this against the checklist, the significant findings here are about efficiency, and about what's missing rather than what's broken.

Starting with Structure and efficiency.

There is no sorting anywhere in this file. No filtering. No pagination.

And here's the bigger point. Nowhere in this entire codebase does any piece of logic compare one record against another record. Every operation touches one document, or all of them. There's no relational reasoning, and no reasoning about time at all.

Back to line 11. The cost of this query grows in direct proportion to the size of the collection. In Big O notation, that's O of n, where n is the number of documents.

Big O notation is just a way of describing how much slower something gets as the data grows. O of n means if you double the data, you double the work.

Right now the database has six seed records, so this is invisible. With fifty thousand trips, this would return fifty thousand documents across the network every time somebody loads the page.

The checklist asks whether storage use is efficient. Returning an entire collection with no pagination is the clearest place in this project where the answer is no.

Next, Documentation and Variables.

Both are adequate in this file. The comments accurately describe what each function does, and the naming is clear.

Next, Arithmetic Operations.

Not applicable again. There's no arithmetic in this file at all.

Next, Loops and Branches.

The branching here is simple and correct. Check whether the result came back empty, return a 404 if it did, otherwise return the data. There's no deep nesting and no missing case.

And finally, Defensive Programming.

The relevant question is whether imported data and input arguments are tested for validity. The trip code comes straight from the URL into the query with no validation.

And I'd argue an unbounded response size is itself a defensive problem. There is no ceiling on how much data a single request can pull back.

So this category is unusual. There isn't really an algorithmic weakness to fix here, because there's almost no algorithm to begin with. My enhancement introduces one.

Algorithms and data structures: planned enhancement

My enhancement for this category is class scheduling conflict detection. This is the first operation in the platform that has to compare records against each other.

The problem it solves is simple. Stop the same teacher being booked for two overlapping class sessions.

The check runs on the server, on both create and update, and it's authoritative. There's no client-side pre-check, because a client-side check can be bypassed, which makes it a convenience rather than a control.

Now, the naive way to do this would be to fetch every session that teacher has ever taught and compare each one to the proposed time. That costs O of n, where n is their total history. It grows without any limit as that history builds up.

And here's the part I want to spend a moment on, because this was the real design decision.

The obvious fix is to add a compound index on teacher and start time, then query for sessions where the start time is before the proposed end, and the end time is after the proposed start. That's logically correct.

But it doesn't actually help. The index can serve the start time condition. It cannot serve the end time condition. So the database would scan every session that teacher has ever taught up to the proposed end time, and then filter the rest in memory.

That's still O of n. The optimization would be completely illusory.

The actual fix is to give the query a lower bound as well as an upper one.

The schema enforces a maximum session length of four hours. So any session that could overlap the proposed window must start no earlier than the proposed start, minus four hours. Once I constrain the start time to that narrow window, the index can seek straight into it.

Locating that range costs O of log n, which grows very slowly. And the number of candidates it returns is bounded by however many sessions one teacher can physically fit into a four-hour window, no matter how long their history is.

So the total cost is O of log n, plus k. And that's a real improvement, not the same cost rewritten.

There's a trade-off, and I want to state it openly rather than present the optimization as free. The bounded query is only correct because the maximum session duration is enforced on every write. A session longer than four hours could start before my lower bound and get missed. So I'm trading full generality for a guaranteed cost ceiling, and paying for it with a schema constraint.

One last detail. When there's a genuine conflict, the request is rejected with HTTP 409 Conflict, not 400. I chose that specifically, because 409 means the request conflicts with the current state of the schedule, whereas 400 would suggest the request itself was malformed.

The skills this demonstrates are stating the cost of an existing approach precisely, recognizing that an apparently optimized query can keep the original cost when the index can't serve every condition, and naming what a performance improvement actually costs.

This aligns with Course Outcome Three, evaluating computing solutions using algorithmic principles while managing trade-offs. I compare two approaches by stated time complexity and I name the constraint that makes the faster one correct.

And it aligns with Course Outcome Four, using well-founded techniques, because compound indexing with a bounded range query is a standard industry technique, and its correctness gets verified by boundary-case tests rather than assumed.

That completes Category Two. Finally, Category Three, Databases.

Databases: existing functionality

This is Category Three, Databases.

The starting files are the two Mongoose schemas in the models folder.

Quick context first. MongoDB is a document database, which means it stores flexible documents rather than fixed rows and columns. It doesn't enforce a structure by itself. Mongoose is the ODM, the Object Data Modeling library, that imposes a defined schema in the application code instead.

This is the Trip schema. Code. Name. Length. Start date. Resort. Price per person. Image. And description.

Two of these fields are indexed: code and name. Both are single-field indexes.

And this is the User schema. Email, name, hash, salt. It's used only for administrator login.

That's it. Two schemas, two single-field indexes, and that's the entire data layer as it exists today.

Databases: code analysis

Analyzing the data layer against the checklist, the findings are about what the schema design doesn't do, plus one security issue in how database content reaches the user.

Starting with Structure.

There is no relationship of any kind between these two schemas. Trip and User have no reference to each other. Nothing joins. Nothing references anything.

The aggregation framework is never used anywhere in this artifact. Aggregation is MongoDB's way of combining and summarizing data across collections. Every query here is a simple find on one collection.

And the only indexes are the two single-field ones I showed you. There's no compound index anywhere, meaning no index that covers more than one field together.

One smaller finding. In the seed script, the data file is read using a relative path. That means the script only works if you run it from exactly the right directory. The checklist asks whether files are checked for existence before being accessed, and here they aren't.

Next, Documentation.

The schemas are readable and the field names explain themselves. No complaints there.

Next, Arithmetic Operations. Not applicable. There's no arithmetic in the data layer.

And now Defensive Programming, which is where the important finding is.

This is the Handlebars template that renders the public travel page. I want you to look at three lines together, because the contrast is right here in the same file.

Line 24. Two curly braces around this.code.

Line 25. Two curly braces around this.name.

Line 26. Three curly braces around this.description.

In Handlebars, two braces escape the content. That means whatever is in there gets displayed as plain text, safely.

Three braces mean do not escape it. The content gets inserted into the page as live HTML.

And that content comes directly out of the database.

So anything stored in a trip description gets rendered as code in the visitor's browser. That's a stored cross-site scripting vulnerability. Stored, because the malicious content lives in the database and gets served to everyone who loads the page.

Right now, creating a trip requires authentication, so the exposure is limited. But in the platform I'm building, teachers will be creating records with free-text fields. That turns this from a theoretical problem into a directly exploitable one.

The checklist asks whether imported data is tested for validity and completeness. Database content reaching a template unescaped is exactly that question, and here the answer is no.

One last item on security. The repository contains a .env file holding the token signing secret. It's correctly excluded from version control by the gitignore file, and I've moved it out of view for this recording. I'm mentioning it because handling of secrets is part of a security review even when it's being done correctly.

So to summarize. The data layer is functional, but it's flat. Two unrelated schemas. No aggregation. Only single-field indexes. And database content reaching the page without escaping.

Databases: planned enhancement

My enhancement for this category introduces three things that don't exist in the original: cross-collection aggregation, a real relationship between collections, and a compound index defined to serve a specific query.

The aggregation produces three reports for the owner and the accountant. Attendance rate per class session. Revenue collected per month. And an attendance-adjusted outstanding balance per student.

That last one needs the billing model defined, and I defined it in the plan rather than leaving it for later.

The school charges per lesson attended. So the rate is stored on the ClassSession, not on the Student, which lets different class types be priced differently. A student's balance is the sum of the rates of the sessions they actually attended, minus what they've paid.

That matters because it makes attendance genuinely drive the financial number, instead of being reported next to it. And it's the reason the pipeline has to join across three collections rather than two.

There are two schema decisions I committed to, and I want to justify both.

First, Attendance and Payment records reference their Student and ClassSession by identifier, rather than embedding that data inside them. These records are numerous, they're created continuously over time, and they get queried independently of the student they belong to. All three of those favor referencing over embedding for this particular relationship.

Second, the compound index on teacher and start time gets defined here. It exists specifically to serve the bounded query I described in Category Two. So this is a database design decision that directly enables an algorithmic improvement somewhere else in the same platform, rather than an isolated indexing choice.

And the reporting interface is matched to whoever is reading it, rather than one generic table for everybody.

The accountant sees monthly revenue as a tabular breakdown with per-student rows, because that output feeds bookkeeping and has to reconcile line by line.

The owner sees attendance rate paired against revenue for the same period, because the owner's actual question is whether a class is worth continuing to run, and neither of those figures answers that alone.

And a teacher sees only their own roster and attendance completion, with no financial data at all, because it isn't relevant to their decisions and it's restricted from their role by the scope rules from Category One.

Choosing a different format for each of those readers is a communication decision as much as a technical one.

The unescaped template output I showed you gets corrected as part of this work as well.

This aligns with Course Outcome One, supporting organizational decision-making, because the reporting is built on actual recorded activity rather than estimates.

It aligns with Course Outcome Two, delivering communications appropriately adapted to specific audiences, because each report is deliberately formatted for the person reading it and the decision they're making.

And it aligns with Course Outcome Three, managing trade-offs in design choices, because both schema decisions — referencing versus embedding, and the compound index — are justified on stated criteria rather than convention.

Closing

That completes my code review for all three categories.

To summarize. One artifact, Travlr Getaways, enhanced across software design and engineering, algorithms and data structures, and databases.

Across the three categories, all five course outcomes are covered. Category One addresses outcomes one, four, and five. Category Two addresses three and four. Category Three addresses one, two, and three.
